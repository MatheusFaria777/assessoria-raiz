## 1. Instagram: sessão pessoal → API oficial (mudança de segurança)

**Problema:** o Uploader baixava posts do Instagram usando o cookie de sessão pessoal do Matheus (`sessionid`), imitando o app mobile via `services/instagram.py`. Funcionava, mas é uso não-oficial da plataforma. A conta pessoal do Matheus recebeu um aviso de restrição por "comportamento automatizado" em 27/07 — consequência direta desse método, mesmo já com csrftoken/ds_user_id corrigidos.

**Fix definitivo:** `services/instagram_graph.py` (novo) — usa a API oficial do Meta (`GET /{instagram_actor_id}/media`), com o mesmo token que já publica os anúncios (System User Token, permissão `instagram_basic` adicionada). Não usa mais cookie nenhum. `routers/uploader.py` foi atualizado pra usar esse módulo no lugar do antigo.

**Limitação conhecida:** só encontra posts recentes (busca por permalink entre os últimos ~200 posts da conta, paginado). Post muito antigo pode não ser encontrado — não é problema pro uso real (carro que acabou de ser postado).

`services/instagram.py` (método antigo) foi deixado no repo, não é mais chamado por ninguém. Pode ser removido num cleanup futuro se quiser.

## 2. Instagram Actor ID — busca automática + bug não resolvido na criação do anúncio

**Novo:** `GET /api/clients/{id}/instagram-lookup?page_id=X` (`services/meta.get_instagram_id_from_page`) busca a conta profissional do Instagram vinculada a uma Página do Facebook, direto da API. Botão "Buscar do Meta" na aba Conjuntos do cliente (ao lado do campo Instagram Actor ID) usa isso — elimina digitar/errar o ID na mão.

**Bug NÃO resolvido:** mesmo com o ID correto (confirmado batendo com o que a própria API retorna), a criação do anúncio (`POST /adcreatives`) falha com `(#100) Param instagram_actor_id must be a valid Instagram account id`. Testado:
- ID validado como correto (usado com sucesso pra ler os posts)
- Conta de anúncios já usada com sucesso antes pra esse cliente (não é conta errada)
- Conectar o ativo Instagram↔Conta de anúncios no Business Manager não resolveu
- Mandar o campo também no nível de cima do `AdCreative` (além de aninhado em `object_story_spec`) não resolveu

**Hipóteses ainda não testadas:** permissão de pessoa↔ativo no Business Manager (aba "Pessoas" da conta do Instagram, separada de "Ativos conectados"); demora de propagação do Meta; conflito entre `instagram_actor_id` e `degrees_of_freedom_spec`/Advantage+ creative enhancements (`profile_card` etc — ver `padroes-campanha.md` da skill meta-ads-ratos, que documenta um caso parecido usando `instagram_user_id` em vez de `instagram_actor_id` pra campanhas de "Visita ao Perfil").

**Mitigação em produção (essa sim funcionando):** `routers/uploader.py` — se a criação do anúncio falhar com esse erro específico, tenta de novo automaticamente sem `instagram_actor_id`. O anúncio sobe igual, só não vem com o Instagram pré-selecionado (precisa escolher manualmente no Ads Manager, do jeito que já era antes). Fila nunca mais trava por causa disso.

## 3. Unificação da classificação de campanhas

**Problema de fundo:** o sistema tinha 4 formas separadas de responder "que campanhas esse cliente tem e qual o tipo de cada uma" — `Adset` (conjuntos, usado só pelo Uploader), `CampaignGroup` (palavra-chave, é quem realmente calculava os números em todo lugar, mas a tela de configuração dele nem tinha rota no frontend), `Client.sheets_tabs` (campo antigo, fallback), e `ClientCampaign`/aba Campanhas (o novo, mapeamento explícito por ID real do Meta — configurável, mas **nunca lido por nada** pra calcular).

**O que foi feito** (arquivos principais: `services/meta.py`, `services/campaign_config.py` [novo], `services/sync_engine.py`, `routers/cadencia.py`, `routers/reports.py`, `routers/sheets.py`, `routers/campaign_mapping.py`, `services/cadencia_builder.py`, `services/report_builder.py`):

- `ClientCampaign` (aba Campanhas) virou a fonte real de cálculo em todo lugar — planilha, cadência, relatório — assim que um cliente é configurado nela. Cliente sem configurar continua no sistema antigo (palavra-chave), sem regressão.
- Campo `label` novo em `ClientCampaign` — nome customizável exibido no relatório, sugerido automaticamente limpando tags do nome real da campanha (`suggest_label()` em `campaign_config.py`).
- Agregação mudou de "por tipo" pra "por nome configurado" (`label`) — duas campanhas/conjuntos com o mesmo nome somam junto (ex: campanha principal + remarketing do mesmo vendedor), nomes diferentes ficam separados mesmo sendo do mesmo tipo.
- Campo `meta_adset_id` novo em `ClientCampaign` (opcional) — permite mapear um CONJUNTO específico dentro de uma campanha, não só a campanha inteira. Resolve o caso de campanha com um conjunto por vendedor. Quando existe mapeamento por conjunto, `get_account_data()` busca insights em `level=adset` em vez de `level=campaign` (a API do Meta retorna ambos os IDs nessa granularidade).
- "Melhores criativos" (cadência de quarta + relatório) também passou a separar por grupo quando há mapeamento configurado — antes era um ranking geral misturado.
- `campaign_config.py` centraliza tudo isso: `get_campaign_map()`, `get_sheet_map()`, `build_tab_candidates()` — antes cada consumidor montava essa lógica na mão, foi isso que causou o desalinhamento original.
- Tipos de campanha (`CAMPAIGN_TYPES`/`VALID_TYPES`) centralizados em `campaign_config.py`, expostos via `GET /api/clients/campaign-mapping/types` — antes existiam copiados em 3 lugares (backend x2, frontend).
- Sugestão automática de tipo a partir do `objective` que o Meta já retorna em "Buscar do Meta" (`suggest_type()`).

**Decisão deliberada, não feita:** apagar `CampaignGroup`/classificação por palavra-chave. Ainda é o fallback ativo pra quase todos os clientes (só 1-2 migrados até agora). A tela órfã (`CampaignGroups.jsx`, sem rota no app) não foi mexida.

**Como migrar um cliente:** Clientes → editar → aba Campanhas → "Buscar do Meta" → escolhe tipo + confere nome de cada campanha (ou expande "Separar por conjunto" pra fazer por vendedor) → Salvar. Passa a valer automaticamente em tudo pra aquele cliente.

## 4. Bug sério: sync diário travava tudo sem salvar nada

**Problema:** `services/sync_engine.py` — `run_daily_sync()`/`run_monthly_sync()` não isolavam erro por cliente e só commitavam no banco uma vez no final do loop inteiro. Um erro de cota da API do Google Sheets (rate limit) num único cliente abortava o processo inteiro, sem salvar nem os clientes que já tinham processado certo antes. Foi a causa real de um cliente aparecer com planilha zerada por semanas (não era cálculo errado, era sync que nunca gravou nada).

**Fix:** try/except isolado por cliente (um erro vira só um erro daquele cliente, não derruba o lote), commit incremental (a cada cliente, não só no final), e um intervalo de 1.5s entre clientes pra não estourar a cota de novo.

## 5. Bugs de autenticação no frontend (2 ocorrências do mesmo padrão)

`Settings.jsx` tinha componentes usando `fetch()` puro em vez do wrapper `api` (`lib/api.js`) que anexa o token de login. Resultado: 401 silencioso, erro "Login necessário" mesmo logado.

- `TokenField` (usado pelos campos Instagram Session ID/CSRF/User ID) — corrigido.
- `MetaSettings` (token Meta Ads, troca pra 60 dias) — corrigido separadamente, mesmo padrão, arquivo diferente, não pego pelo primeiro fix.

Rodei `grep` no frontend inteiro depois pra confirmar que não sobrou mais nenhum `fetch()` direto pra rotas autenticadas (os que sobraram são de formulários públicos e login, que não precisam de token mesmo).
